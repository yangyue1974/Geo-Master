# GEO v0 — 可行性分析与对 spec 的偏离

> 这份文档记录:哪些地方按 spec 实现了,哪些地方**没有**按 spec 实现,以及为什么。
> 每一处偏离都对应一个会在 Day 30 咬人的具体问题。

---

## 结论

闭环能跑通。spec 的整体架构成立,tier 的划分方式(按问题形态而非歌手知名度)是这份 spec 里最正确的一个判断 ——
它把"跟维基百科抢主题目"这个必输的仗从实验设计里剔除了。

但有 5 处问题会在 Day 30 咬人,其中 2 处是尺子本身的问题。尺子错了,后面全白做。

---

## 1. 顺序错了 — B5 必须最先跑

**spec 的排法**:W1「模块 A 全部 + B5 体检 → 产出基线报告」。

**问题**:如果 `gospelhub.love` 的 robots.txt 封了 PerplexityBot,或实体页是客户端渲染,
那么基线跑出来的 0% 是**「被封的 0%」**,不是**「被忽略的 0%」**。

这两件事对应完全不同的修复方案:
- 被封 → 改 robots.txt,一行的事,改完重跑
- 被忽略 → 做内容资产,一个月的事

而你会在花完预算跑完 600 次调用之后才发现是哪一种。B5 是 30 分钟的工作。

**实现**:`geo audit` 是 CLI 帮助里的第 1 步。发现 blocker 时进程退出码为 2,
`DEPLOY.md` 顶部会显著标注「先修这些,再谈部署」。

---

## 2. 尺子的透传假设没验证就当前提用了

**spec 的原文**:「`citations` 数组直接给出被引 URL,经 OpenRouter 完整透传,量化最干净」。

**问题**:这是一个待验证的经验断言,不是事实。OpenRouter 把 Perplexity 的引用放在非标准字段,
不同时期在 `body.citations` / `choices[].message.annotations` / `body.search_results` 之间飘;
`gpt-4o-search-preview` 在 OpenRouter 的在售状态也会变。

如果透传形态变了,整批基线数据会静默地全 0 —— 而 0 会被误读成「我们没被引用」,
实际是「尺子没读数」。

**实现**:
- `geo verify` 是独立的第一步:一题打穿所有引擎,原始 JSON 全量落盘到 `data/_verify/`,
  列出 extractor 提到几条、走的哪个字段(`via`),以及**深度扫描发现的所有 URL 字段路径**
  —— 后者用来发现 extractor 漏掉的新字段。
- extractor 不赌任何单一字段,按已知路径依次扫,每条引用记录来源 `via`。
- 只有 `via=text`(正文兜底)命中时判为不通过 —— 那等于结构化引用一条都没拿到。
- 评分阶段也会汇总 `via` 分布;全部来自 `text` 时报警。

**顺带修掉的一个坑**:Gemini grounding 返回的是 `vertexaisearch.cloud.google.com` 的跳转 URL,
真实域名不在 URL 里。直接按 host 判定会把所有引用算成 Google 自己。
`util/url.ts` 里对跳转包装做了识别,从 `web.title` / `web.domain` 兜底解析。

**禁令的实现**:`:online` 插件在构造引擎时就抛异常,而不是跑完 600 次调用之后才发现。

## 3. 「变化量才是结论」原来只是一句话,现在是一个判据

**spec 的做法**:每题每引擎跑 2 次,被引域名取并集降噪。诚实边界里写「变化量才是结论依据」。

**问题**:取并集丢掉了这两次之间最有价值的信息 —— **它们的分歧程度就是噪声底噪的直接测量**。
如果同一题两次跑出的域名只有 40% 重合,那么任何小于这个幅度的前后变化都不能称为结论。
没有这个数字,「变化量才是结论」就只是一句修辞,读报告的人无法判断 3/50 到底算不算信号。

**实现**:`QueryEngineScore.agreement` = 两次运行被引域名集合的 Jaccard。
- 基线报告第 2 节报中位数,并给出判读门槛
- diff 报告第 0 节取各轮最差值作为门槛,逐格标注「超出噪声」/「噪声内波动」

刻意只在恰好 2 次成功运行时计算 —— 3 次以上取两两平均会掩盖极端分歧,而我们要测的正是最坏情况的抖动。

## 4. control 档的作用被低估了

**spec 的定位**:「预期输给维基百科,作对照组」。

**问题**:这个定位只用了它一半的价值。control 档的修复量为零,所以它的对手结构在 D0/D15/D30
之间**应当基本不变**。如果它大幅变化,说明引擎自己换了检索行为 ——
那么 detail / aggregate 的变化就不能全部归因于 fixpack。

换句话说:**control 档是尺子漂移检测器**,这比「对照组」重要得多。

**实现**:
- `ScoresFile.controlCompetitors` 单独统计 control 档的对手榜
- 基线报告第 4 节把它标为「复测时的比对基准」
- diff 报告第 4 节算 control 对手榜的 Jaccard;低于 0.6 时直接判定「本轮结果只能作为观察记录,不能作为结论」

## 5. fresh 档的题库冻结与语义冻结互相冲突

**spec 的做法**:题库一经生成即冻结,所有复测用同一份文件。fresh 档含「本月新发行」类题目。

**问题**:`What are the new gospel releases this month?` 在 Day 0 和 Day 30 **不是同一个问题**。
题面字符串冻结了,语义没有。这 30 题的前后对比是无效的,但它看起来完全正常。

**实现**:`Query.timeSensitivity` 三分类:
- `none` — 与时间无关,完全可比
- `entity-relative` — 「{artist} 的最新单曲」,实体固定,语义随时间漂移但仍可比
- `window` — 「本月新发行」,不可严格比较

`window` 类题目照跑照记录,但在 diff 报告里被移出主对比表,单列在第 5.1 节,明确标注「只作观察」。

## 6. A1 的输出撑不起 A3 的题库(spec 的一处断裂)

**spec 的 entities.json**:`[{ type, name, url, aliases }]`。

**spec 的 detail 档题目**:「某首歌收录在哪张专辑」「发行日期」「按时间排列的完整专辑序列」。

**问题**:那些关系数据在 sitemap 模式下没有来源。entities.json 里根本没有这些字段。

**实现**:`Entity.facts` 字段,抽取器三级降级:JSON-LD > microdata > 启发式(title/h1/meta)。
每条事实标注来源。题库生成器**按实际可用事实决定能出哪些模板题** —— 事实不足就少出题。

题量随站点数据丰富度浮动是正确行为,不是 bug。少出题好过出假题:
一道基于虚构歌名的题从出生就是废的,而你在 Day 30 之前不会发现。

---

## 7. A3 没有贯彻 B1 的反幻觉原则

**spec 的 B1**:「数据只允许来自库内事实,任何字段无数据即跳过,**严禁模型补全编造**」。

**spec 的 A3**:「用 Claude API,对每个抽样实体按模板生成自然语言查询」。

**问题**:同一个风险在 A3 没有堵。模型很容易生成一首库里不存在的歌 ——
`Which album is "Amazing Grace Reprise" by Mary Hale on?`,而这首歌不存在。

**实现**:
1. 题目由模板 + entities.json 里的确凿事实**确定性填充**(可复现、零幻觉)
2. 模型只做两件受约束的事:挑主题词(明确禁止专有名词)、把机械句式改写得像普通乐迷说话
3. **改写结果必须仍包含原实体名字符串**(以及引号内的歌名、四位数年份),否则丢弃回退到模板原文
4. 抽样用种子 PRNG,同样输入必然得到同样题库(e2e 里有断言)

默认走纯模板,`--paraphrase` 才启用改写。

## 8. 归因:本实验是单臂的

B1(JSON-LD)/ B2(llms.txt)/ B3(内容资产)/ B4(索引推送)在 Day 0 一次性全部上线。
若引用率上升,**无法区分是哪一项起作用**,也无法排除站点自然增长。

真要归因需要分批上线(比如 aggregate 页 Day 0 上、detail FAQ 块 Day 7 上),
但 30 天窗口太短,分批会让每个臂的观察窗口不够。

**判断**:v0 不追求归因,追求「机器是否转动」。这个取舍是对的。
但必须写进报告,否则报告读起来会像是证明了「JSON-LD 有用」,而它证明不了。

**实现**:`report/bounds.ts` 里的第 4 条诚实边界(spec 原本只有三条)。
第 5 条是尺子自身漂移的边界。

## 9. 成本

150 题 × 2 引擎 × 2 次 = 600 次调用。sonar-pro 的定价结构是 token 费 + 每请求的检索费,
实际一轮大约 **$8–20**。$50 的护栏是宽松的。

**但护栏得真实现**:OpenRouter 只有在请求里显式带 `usage: {include: true}` 时才回传真实 cost。
不带的话 `usage.cost` 永远是 undefined,护栏就是瞎的。`engines/index.ts` 里默认带上了;
拿不到 cost 的调用按 $0.02/次 估值计入,避免护栏被静默绕过。

## 10. 「对任意网站跑通」这个约束的现实边界

验收清单第一条要求探针仅凭一个 sitemap URL 就能对任意网站跑通。这个约束是对的
(未来的客户只有 URL),但「按 URL 模式识别实体页」需要有人告诉它模式长什么样。

**实现**:`geo extract --propose` 按路径前缀聚类,给出候选模式 + 样本 URL,人确认后写进 site profile。
这是「自动提议 + 配置覆盖」的中间态 —— 全自动识别不可靠,全手工配置不 scale。

`sites/smoke-anthropic.json` 是为验收清单第一条准备的第三方站点配置。

## 11. 关于 GospelHub 的代码改动

spec 说「对 GospelHub 额外生成可直接合并的代码改动」。

**没有这样做,理由**:生成能干净合入某个仓库的 patch,需要知道那个仓库的目录结构、
命名约定、数据层形状。这边都不知道。承诺自动 patch 只会产出合不进去的 diff,
比明确说「这是片段,请人工接线」更浪费时间。

**实现**:`fixpack/output/{site}/nextjs/` 是可直接拷贝的完整文件 + 明确的接入位置说明,
数据层调用处标了 `TODO`。README 里写清了三处接线点和两条硬约束
(无数据即跳过、问答块必须可见)。

## 12. 线上实测推翻的两个假设(2026-07-29)

对 gospelhub.love 实跑 `--propose` 与 `extract` 之后,有两件事和 spec 的设想不同。

### 12.1 这个站的主体是演出,不是专辑

sitemap 461 个 URL:`/concerts/` 270、`/artists/` 129、`/releases/` 58,**没有独立歌曲页**。
spec 假设的 artist / album / song 音乐库只对上了一部分,而最大的一类 —— 演出 —— 完全没被预见。

这不是坏消息。演出同时占满三个可赢维度:

- **地域**:「纽约有哪些 gospel 演出」
- **时间窗口**:「八月有哪些」—— 而且都是未来的日期,维基百科在这一档不是滞后,是根本没有
- **实体关系**:`performer` 字段带 URL,把演出和歌手连起来 ——「X 接下来在哪演」

三类问题都没有任何百科页面能回答,引擎必须找一个现成的列表页。这比专辑元数据好赢得多。

因此新增:
- 事实抽取支持 `MusicEvent`(`startDate` / `venue` / `city` / `country` / `performer` / `performerUrl`)
- 三个题库模板:`artist-touring`(fresh,entity-relative)、`concerts-city`、`concerts-month`(aggregate)
- 三类聚合页:按城市、按月份、按歌手的巡演页

两条约束照旧:只收**未来**的场次(列一堆过期演出会直接损害页面的可引用性);
月份写进题面(`August 2026` 而不是「本月」),让这道题在复测时仍问同一件事。

`ENTITY_TYPES` 里 `MusicEvent` 必须排在 `MusicGroup` 之前 —— 演出页的 JSON-LD 里嵌了一个
`MusicGroup` 的 performer,顺序反了就会把演出者当成实体本身。

### 12.2 去重把 43% 的演出场次静默丢掉了

原来的去重键是「类型 + 名称」。对歌手和专辑成立,对**事件不成立**:
一个巡演有很多场,每场标题相同但日期场馆不同。270 个演出页只有 154 个不同标题,
按名字去重直接丢掉 116 场 —— 而那正是 fresh 档最值钱的数据。

修法:key 里加**身份判别符** —— 能区分两个同名实体是否为同一事物的事实(`startDate` / `venue` / `city`)。
歌手没有这些字段,行为与从前一致(取事实最丰富的那份);演出有,于是同一巡演的不同场次各自保留。

刻意不把 `description` / `genre` 放进 key:它们的差异是丰富度差异,不是身份差异。

### 12.3 顺带修掉的路径撞车

fixpack 默认生成 `/releases/{year}` 作为按年份的聚合页,
但 `/releases/*` 已经是这个站专辑详情页的命名空间。撞车在两个方向上都是静默的:
新页面被现有路由吃掉,而且下一轮抽取会把聚合页当成实体收进 entities.json。

聚合页路径改成 site profile 上的可配置模板,`buildFixpack` 在任何 IO 之前检查冲突并拒绝生成。

### 12.4 已确认成立的部分

- 实体名是真名,不是 UUID(页面 JSON-LD 完整)
- `sameAs` 指向 Wikipedia / Spotify / Apple —— 这些歌手都有维基条目,**control 档必输的预判有了实证依据**
- 专辑有 `artist` + `datePublished`,`release` / `year-list` / `chronology` 三个模板有支撑
- 库是活的:抽到的专辑里有 19 天前发行的
- robots.txt 干净 —— 没封任何抓取器,而且声明了 sitemap

### 12.5 仍未验证

- artist 的 JSON-LD 里**没有**专辑列表,`chronology` 能否出题取决于 album 实体的 `facts.artist` 反查。
  129 个歌手 : 58 张专辑,多数歌手名下一张专辑都没有 —— 这一档题量会很少。
- 实体页的裸 HTML 渲染状况(B5 的 CSR 检查)还没在配好 `entityPatterns` 之后重跑过。
- 引擎透传(`geo verify`)一次都还没跑 —— 尺子尚未验证。

## 已知的、没有解决的问题

1. **API 端 ≠ 客户端。** ChatGPT / Perplexity 网页端与 API 端走的不是同一条检索链路。
   这个差距无法通过工程消除,只能在报告里声明,并坚持「只看变化量」。

2. **30 天可能不够。** Bing / Google 的索引周期不确定,新页面进索引本身就可能超过 15 天。
   如果 Day 30 时 aggregate 页还没进索引,得到的 0 是「没进索引」而不是「进了没被引用」。
   缓解:B4 的 IndexNow 推送 + GSC 手动请求编入索引,并在 Day 15 用 `site:` 查询确认收录状态。

3. **样本量小。** 每档 30–50 题,单站点,无外部对照。detail 档从 0/50 变成 3/50 时,
   噪声底噪指标能告诉你这算不算信号,但给不了统计意义上的置信区间。v0 接受这个限制。

4. **`credits` 模板大概率出不了题。** 库里如果没有创作/制作署名字段,
   这一类题一道都不会生成,B3 也不会生成对应问答。这是正确行为,
   但意味着 detail 档实际题量可能明显低于 50。
